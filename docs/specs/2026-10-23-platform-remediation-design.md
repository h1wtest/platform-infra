# Переработка учебной микросервисной платформы

Статус: утверждён пользователем; реализация в отдельных рабочих ветках.

## Цель и границы

Исправить все категории проблем аудита существующего h1wtest, сохранив обязательные Rust, Go, Kafka-совместимый брокер и React. Структуру можно менять. Результат — воспроизводимая локальная платформа с проверенными бизнес-сценариями, безопасностью, обработкой отказов и документированными ограничениями. Термин production-ready не применяется без проверки соответствующей среды.

Не создавать платные облачные ресурсы, не обращаться к production, не публиковать новые GitHub-репозитории и не пушить изменения без отдельного разрешения. Новые локальные сервисы допустимы. Не уничтожать существующие пользовательские данные. Испытания потери данных и восстановления выполняются на изолированных ресурсах с уникальными именами.

## Архитектура и владение

1. `identity-service` (Rust): учётные записи, пароли, подтверждение email, смена и восстановление пароля, MFA, recovery codes, сессии, refresh rotation/reuse detection, OAuth/OIDC, RBAC. Владеет identity DB и ключами подписи. HTTP для браузера, защищённый межсервисный API для проверки доступа и административных команд.
2. `profile-service` (Go): профиль и настройки уведомлений; своя БД и роль, асинхронное создание профиля по регистрации. Не читает identity DB. API не доверяет одним лишь полям JWT: проверяет действительность сессии через identity с ограниченным deadline и fail-closed.
3. `notification-service` (Go): приём событий, создание durable delivery jobs, worker доставки email/Telegram, retry/DLQ/replay, история статусов. Своя БД. HTTP управления/health и worker — отдельные deployments, чтобы масштабирование API и внешней доставки не зависело друг от друга. Для разработки email — Mailpit. Telegram использует настоящий Bot API и проверяемую привязку аккаунта; без токена бота канал явно недоступен, не имитирует доставку и не считается принятым. Реальная Telegram-приёмка требует предоставленного пользователем bot token и тестового чата; отсутствие credentials фиксируется как внешний незакрытый gate.
4. `admin-audit-service` (Go): durable audit projection, защищённый административный API чтения и команд управления пользователями/доставкой. Своя БД. Решение RBAC принимает identity; административные команды не принимают произвольный user_id за полномочия вызывающего.
5. `frontend` (React/TypeScript): пользовательские сценарии и административные экраны; единый same-origin HTTPS gateway. Без долгоживущих bearer secrets в localStorage.
6. `platform-contracts`: версионируемые межсервисные API и схемы событий, генерация, lint и breaking checks. Реализации используют эти контракты, а не вручную дублируемые структуры.
7. `platform-infra`: сборка, окружения, Kubernetes, bootstrap/migrations, проверка готовности, секреты, наблюдаемость, backups, приёмочные команды.

Зависимости направлены от application к доменным портам, adapters реализуют порты. Явная сборка зависимостей. Без распределённых транзакций, универсальных framework-обёрток и сервисной сетки ради количества технологий.

## Identity и безопасность

- Argon2id вне async executor с ограниченной параллельностью; ограничения входного размера, нормализация email, публичные ошибки без SQL/секретов, rate limits для login/register/verification/MFA/recovery.
- Access tokens с асимметричной подписью, iss/aud/exp/iat/sid/token-use, фиксированным допустимым алгоритмом и kid. JWKS содержит только публичные ключи. Ключи сохраняются вне Git; предусмотрены активный и предыдущий ключи для ротации.
- Проверка доступа учитывает отзыв, ban и срок сессии во всех HTTP и межсервисных путях. Ошибка источника проверки не разрешает доступ. Отзыв не зависит от истечения access token.
- Владелец сессии проверяется атомарно перед отзывом. Logout завершает серверную сессию, а не только очищает UI.
- MFA setup не меняет действующий секрет до подтверждения; изменение действующего MFA требует свежего подтверждения. Pending challenge и recovery codes одноразовые, TOTP защищён от повторного использования; бан повторно проверяется при завершении MFA.
- Восстановление пароля: не раскрывающий существование аккаунта ответ, одноразовый короткоживущий token с хешем в хранилище, доставка через durable job, атомарная смена password hash и отзыв сессий. Смена пароля требует свежей аутентификации; оба сценария аудитируются.
- Refresh rotation атомарна; reuse отзывает семейство. Параллельные попытки не создают две действующие ветви.
- Браузер использует HttpOnly Secure same-site cookie для сессии/refresh и короткоживущий access token только в памяти при необходимости. Мутации с cookie защищены Origin/CSRF; CORS не wildcard.
- Внутренние endpoints имеют проверяемую service identity, ограниченные права и TLS. Для административных действий дополнительно требуется пользовательская авторизация и свежий MFA.
- Secrets генерируются локально, не выводятся в логи, не коммитятся. Отдельные роли БД и migration/runtime credentials. Секреты, ранее закоммиченные как defaults, больше не принимаются как production configuration; история Git не переписывается без разрешения.

## OAuth/OIDC

Authorization Code + PKCE S256, точное сравнение зарегистрированных redirect URIs, public/confidential clients с соответствующей аутентификацией, nonce/state с корректным URL encoding. Стандартный browser authorization redirect/login flow, form-encoded token endpoint и корректные OAuth ошибки. Discovery объявляет только реализованные grant types и auth methods. Поддерживаемый refresh grant использует тот же безопасный механизм rotation. ID token и userinfo содержат только разрешённые scope claims. Не заявлять сертификацию OIDC без сертификационного прогона.

## События и доставка

- Изменение authoritative SQL state и outbox event выполняются одной транзакцией. Redis — не обязательный второй commit для регистрации; временные identity challenges хранятся с согласованным authoritative state.
- Единый event_id для outbox и envelope, aggregate key, версия, время и W3C trace context. Никаких кодов подтверждения в общедоступном audit event: delivery intent отделён и защищён правами/ограниченным хранением.
- Relay использует durable claim/lease либо корректно удерживаемую транзакцию; после crash неподтверждённая работа доступна повторно. Публикация at-least-once, порядок по ключу агрегата, распределение по партициям, bounded retry и наблюдаемый backlog.
- Consumers подтверждают только успешно сохранённые результаты. Inbox event_id и локальные изменения коммитятся атомарно. Некорректное событие не молча пропускается: durable quarantine/DLQ с причиной и контролируемым replay.
- SMTP и медленные внешние вызовы не выполняются в Kafka poll loop. Worker берёт delivery job с lease, ограниченным timeout и persisted attempts/next_attempt_at.
- При временной ошибке — exponential backoff с jitter; при постоянной/исчерпании попыток — terminal failed/DLQ. Replay авторизован и аудитируется.
- Exactly-once SMTP не обещается: при падении после принятия письма провайдером и до локального commit возможен повтор. Стабильный Message-ID, отслеживание неоднозначного исхода и идемпотентный provider key там, где провайдер его поддерживает.

## Инфраструктура

- Локальная среда явно local/dev, не `environment: production`. Сборки повторяемы: lockfiles, pinned toolchain/base images, immutable application tags/digests; без latest и скрытого go mod tidy при сборке.
- Bootstrap последовательно создаёт secrets/DB roles, применяет версионированные migrations под lock и запускает приложения. Любая ошибка прерывает запуск; никаких `|| true` для обязательных шагов. Существующая схема не сбрасывается.
- Stateful services имеют PVC и понятную стратегию обновления. Резервные копии PostgreSQL и восстановление в отдельную БД проверяются сравнением данных. Политика хранения, encryption/access и RPO/RTO описываются измеренными результатами, не рекламными обещаниями.
- HA PostgreSQL/брокера и размещение реплик конфигурируются для выбранной среды; локальные контейнерные ноды одного компьютера не считаются независимыми зонами отказа. Нельзя утверждать устойчивость к потере хоста по тесту удаления пода.
- Liveness проверяет жизнеспособность процесса; readiness — возможность выполнять обязательный контракт (schema/dependencies/worker state). Деградация Kafka не обязана блокировать identity login, пока durable outbox способен принимать события; границы деградации явные.
- NetworkPolicy default-deny с необходимыми DNS/API/DB/broker/egress исключениями; выделенные ServiceAccounts, минимальный RBAC, без automount токена где он не нужен, non-root, dropped capabilities, seccomp и read-only filesystem где поддерживается.
- TLS gateway и внутренних чувствительных соединений. Dashboard не включён по умолчанию; доступ временный и минимально привилегированный, без постоянного cluster-admin token.
- PDB, topology spread/anti-affinity, ресурсные requests/limits и HPA по подходящим сигналам. CPU utilization считается относительно requests, не мощности хоста; consumer capacity ограничена partitions.
- AWS не разворачивается в рамках локальной приёмки. Документация разделяет pod scaling и node scaling, фиксирует будущие cloud prerequisites и не выдаёт локальные испытания за проверку EKS/RDS/MSK.

## Наблюдаемость и поставка

Структурированные редактируемые логи, W3C trace propagation HTTP → outbox → Kafka → jobs → delivery, OTLP collector и доступный trace backend. Метрики HTTP errors/latency, outbox age, Kafka lag, delivery retries/failures, DB pools, readiness. Дашборды и проверяемые алерты; SLO определяются для пользовательских операций, а не discovery.

CI проверяет формат/lint/build, поведенческие unit/integration/security/contract tests, зависимости и секреты, сборку immutable images и Kubernetes config. Независимые workflows сервисов; управляемая совместимость контрактов. Автоматическая поставка ограничена проверяемой тестовой средой; публикация в пользовательские удалённые ресурсы требует разрешения.

## Приёмка

1. Чистый изолированный старт и повторный bootstrap без потери данных, валидные migrations; процесс с отсутствующей схемой не Ready.
2. Через реальный UI/API: регистрация → Mailpit → подтверждение → профиль → login → уведомление → настройки.
3. MFA enable/login/recovery/replay, повторный setup, смена MFA и запрет небезопасных путей.
4. Два пользователя: запрет чтения/отзыва чужих сессий; logout/revoke/ban прекращают доступ по старому token; проверка в identity/profile/admin.
5. Стандартный внешний OIDC consumer: discovery/JWKS/signature, PKCE, redirect/nonce, scopes, refresh и reuse, неверные client/redirect/verifier.
6. Дубликат события, конкурирующие relay/consumers, crash на границах commit, недоступные Kafka/SMTP/DB, poison event и replay: наблюдать сохранённый state и отсутствие потери логических операций.
7. Пересоздание stateful pod сохраняет disposable данные; backup восстанавливается в отдельном ресурсе с проверкой содержимого. Деструктивные сценарии не затрагивают существующие данные.
8. Нагрузка на реальные login/profile/delivery сценарии с latency/error/lag, не только discovery. Chaos обязан подтвердить фактическое внесение отказа, восстановление и целостность результата.
9. Визуальная проверка frontend и административных путей, логи/метрики/трейсы и срабатывание тестового алерта.
10. Независимое ревью изменений; если reviewer недоступен, это явно отмеченный незакрытый gate, а не выдуманное одобрение.

## Последовательность

Контракты и ownership → identity/security/data transactions → profile/notification/admin adapters → инфраструктура и миграции → UI/OIDC consumer → наблюдаемость/CI → полная приёмка и независимое ревью. В каждом блоке регрессия воспроизводится до исправления и проверяется после. Итоговый отчёт перечисляет фактически выполненные сценарии и оставшиеся внешние prerequisites.
