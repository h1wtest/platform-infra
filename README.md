# Изолированная локальная платформа

Среда **local/dev**, кластер и namespace `sso-remediation`. HTTPS `https://localhost:8448`, HTTP `http://localhost:8089` перенаправляет на HTTPS. Старые кластеры, namespace и тома не изменяются. Docker Compose и прежние permissive manifests удалены из cutover; постоянный Dashboard cluster-admin и токен больше не provisionятся. Уже существующий чужой Dashboard автоматически не удаляется.

## Предварительные условия

Linux x86_64/WSL2, Docker Desktop/Engine, curl, OpenSSL, make, Python3.12+, uv0.13.5, Helm4.3.1, k3d5.9.0, kubectl1.36.1 (minor34–36). Новый bootstrap фиксирует K3s1.35.9-k3s1; существующий stand1.35.5 не обновляется/удаляется автоматически и отмечается maintenance gate. CNPG1.30.1 поддерживает Kubernetes1.34/1.35/1.36 и PostgreSQL14–18 по [официальной матрице](https://cloudnative-pg.io/docs/current/supported_releases/); PostgreSQL18.6-standard-trixie. `bash scripts/bootstrap-tools.sh` устанавливает checksum-проверенные binaries в `~/.local/bin` без sudo/globalCA. `export PATH="$HOME/.local/bin:$PATH"`. Docker рекомендуется≥16GiRAM; Tempo3.1.1 требует headroom до4Gi. Requests/limits описаны в `charts/`, параметры окружения — в `scripts/release_values.py`.

Рядом должны находиться `identity-service`, `user-notification-service`, `frontend`, `platform-contracts`. Docker contexts ограничены owner whitelist; lockfiles обязательны. Registry pins задают исходные PG18.6, CNPG1.30.1, Redpanda26.2.5, Mailpit1.32.0, Prometheus3.15.1, Grafana13.2.4-distroless-slim, Tempo3.1.1, Collector0.163.2 и nginx1.30-alpine. Gateway/Grafana/Tempo/CNPG используют сохранённые исправленные local builds. `build` фиксирует content-addressed tag/imageID, base, hashes recipe inputs и sourceSHA в `.local/images.lock.json`; изменения source/base/recipe требуют rebuild. CNPG release проверяется по official assetSHA256. По решению владельца сканирование уязвимостей образов и зависимостей удалено и не выполняется; старые отчёты — только история, не критерий приёмки. Это не утверждение об отсутствии уязвимостей.

```sh
make bootstrap
make build
make up
make check
make bootstrap-owner
make mailpit       # отдельный терминал, loopback127.0.0.1:28026
make prometheus    # отдельный терминал, loopback127.0.0.1:29090
make grafana       # отдельный терминал, loopback127.0.0.1:23000
make tempo         # отдельный терминал, loopback127.0.0.1:23200
```

Canonical credentials/private keys хранятся в ignored owner `.env` (0600): инфраструктура — `platform-infra/.env`, identity/admin bootstrap — `identity-service/.env`, Go profile/notification/admin/audit и Telegram — `user-notification-service/.env`. Имена перечислены без значений в owner `.env.example`. `ADMIN_EMAIL`/`ADMIN_PASSWORD` задаются в identity env; `TELEGRAM_BOT_TOKEN` и `TELEGRAM_WEBHOOK_SECRET` — только в Go env. Для первого bootstrap также поддержаны process admin credentials. Повтор bootstrap сохраняет credentials и не меняет пароль пользователя. Admin bootstrap требует MFA. `MFA_ENCRYPTION_KEY` доступен только identity; canonical `DELIVERY_ENCRYPTION_KEY` хранится в identity env и передаётся только identity/notification/worker; quarantine keys разделены по Go owner. `.local/` (0700) содержит derived PEM mounts, публичные сертификаты и защищённые historical recovery archives, не второй активный credential store. PEM в `.env` кодируются JSON-compatible quoted strings с escaped newlines; backup key сохраняется побайтно, включая завершающий newline. Не печатайте содержимое `.env`. Telegram token optional: без него канал недоступен. Для настоящей приёмки нужны bot token/chat и публичный HTTPS callback; localhost не подходит.

Первый запуск с legacy `.local/secrets.json` импортирует все credentials/private bytes без rotation, проверяет сохранённые owner env и только затем удаляет legacy файл. Прерывание оставляет возможность безопасно закончить импорт. После миграции отсутствие/пустое required значение или owner `.env` — ошибка, не генерация новых credentials. Редактируйте Telegram token непосредственно в `user-notification-service/.env`; следующая загрузка использует это значение (для running pods примените конфигурацию штатным `make up`). Не копируйте общий `.env` между owners и не передавайте секреты frontend. `.env` исключён из Git, Docker contexts, source exports и workspace hash.

Перенос хранения не является rotation API: `make up` до публикации любых Secrets сравнивает существующие stateful credentials с owner `.env`. Изменения PostgreSQL superuser/DB runtime/migration passwords, Kafka bootstrap password и purpose encryption keys блокируются с требованием отдельной явной rotation/recovery процедуры; новые значения не применяются поверх существующих DB/ciphertext. `ADMIN_EMAIL`/`ADMIN_PASSWORD` — bootstrap inputs, не способ сменить пароль существующей учётной записи. Обычное редактирование Telegram token поддержано; произвольные runtime template variables не обещаются как автоматический rotation интерфейс.

CA `.local/ca.crt` доверять явно через `curl --cacert` или отдельный browser profile. Каждому сервису выдаётся отдельный private key/cert в `.local/certificates/<service>/`; сертификат profile не удостоверяет identity. Только gateway имеет SAN localhost/127.0.0.1; broker SAN соответствуют short/full advertised DNS. Gateway проверяет upstream hostname и устанавливает X-Gateway-Token только identity (остальным upstream пустой), identity доверяет X-Real-IP только с этим secret. Общая CA не означает общий private key. PostgreSQL DSNs требуют `sslmode=verify-full` и CNPG-generated CA `/run/postgres/ca.crt`; host `postgres-rw.sso-remediation.svc`. Kafka29092 и interbroker RPC шифрованы TLS, SASL SCRAM-SHA256, ACL exact topic/group: profile/audit читают только public events; notification также encrypted commands; identity только производит. Bootstrap broker user доступен только broker/admin orchestration; admin listener9645 loopback и require-auth,9644 доступен только Prometheus по policy. Gateway блокирует произвольные /internal и /metrics, исключение — защищённый Telegram webhook.

Создание SASL users выполняется через loopback port-forward к3явно известным broker pods: orchestration читает controller leader_id, проверяет node_config выбранного pod и отправляет mutation только его localhost endpoint. HTTP redirects отключены; Authorization никогда не пересылается на адрес из Location. Смена лидера в момент mutation приводит к fail-closed ошибке, не открывает Admin API наружу.

Если существующий local CA создан без RFC-required keyUsage, strict Python/OpenSSL корректно отклоняет цепочку. Явная команда `make repair-certificates` переиздаёт CA и server certs с правильными critical extensions, сохраняя private keys, subject, serial и SAN; старые certificates архивируются, новые строго проверяются до атомарной публикации. Далее повторно примените TLS Secrets и перезапустите соответствующие deployments/stateful broker по очереди; CA не устанавливается глобально. Клиентские strict проверки не отключаются.

Bootstrap: новый cluster → CNPG controller → durable infrastructure → готовый DB/broker → отдельные migration/runtime роли и DB → конечные migration Jobs → топики → приложения. Миграции запускаются отдельными credentials; runtime получает DML/sequence privileges без CREATE. Ошибка mandatory шага останавливает команду. Jobs сохраняются сутки для диагностики, не игнорируются. Readiness приложений проверяет схему, liveness — процесс. Broker outage не должен ломать identity login, если SQL outbox может сохранять операции.

После смены operator image один `ClusterReady` недостаточен: CNPG ещё может обновлять bootstrap/instance-manager на существующих pod. До provisioning/migrations `up` ждёт все фактические Cluster-owned instances с выбранным image, завершённым init и PostgreSQLReady, согласованными counts/primary; затем проверяет writable primary и повторно сверяет pod UID. Deadline300s ограничивает API/SQL probes. Мутирующие provisioning/migration SQL при ошибке не повторяются и не маскируются.

Migration/rekey Job использует bounded initContainer из pinned PostgreSQL image: тот же pod IP/labels и verify-full DSN выполняют `SELECT1` до60секунд, чтобы дождаться реализации NetworkPolicy для нового pod. Только TCP refused/timeout/DNS transient ошибки допускают повтор; authentication/TLS/SQL ошибки останавливают Job сразу. Собственно migration не повторяется и её ошибка не скрывается. Это необходимо потому, что kube-router применяет IP sets асинхронно после admission; положительные TCP controls проверены на всех3нодах, untrusted control запрещён и к ServiceIP, и напрямую к primary.

Legacy shared-key cutover не автоматический: сохранённый `ENCRYPTION_KEY` блокирует bootstrap/up. Явный `make rekey` также поддерживает ещё не импортированный legacy `.local/secrets.json`; он не является runtime fallback. Только для **никогда не использованных** credentials `make rekey ARGS=--unused` проверяет отсутствие namespace и retained PV и архивирует старый ключ0600. Для populated среды команда требует drain outbox/jobs, committed=end всех6 sensitive topic partitions и истечения уже настроенного Kafka retention (start=end; без truncation/deletion). Затем останавливает writers, повторно проверяет drain, делает encrypted backup и выполняет idempotent transactional rekey каждого DB owner. Старый ключ сохраняется до успеха всех owners и в protected historical archive для старых backup. Ошибка оставляет runtime остановленным и recovery material сохранённым; после успеха `make up` применяет purpose keys и возобновляет runtime. Это maintenance cutover, не прозрачный runtime fallback.

Owner `.env` и historical recovery manifests публикуются атомарно: same-directory0600 tempfile → flush/fsync → os.replace → directory fsync. Перед первым owner rekey Job сохраняется protected полный `.local/rekey-precommit-*.json` (legacy плюс все target keys); финальный archive также содержит весь key manifest. Crash после DB commit не теряет target keys. Не удаляйте precommit/final manifests без проверенной защищённой копии; они столь же чувствительны, как owner `.env`, но никогда не являются активной конфигурацией.

## Независимые Helm-релизы и обновления

Persistent workloads имеют единственный источник манифестов — реальные Helm-шаблоны в `charts/`. Python собирает values из owner `.env` и lockfiles, проверяет local cluster identity, устанавливает проверенный CNPG operator и выполняет provisioning/одноразовые Jobs. Он больше не генерирует параллельные Deployment/Service/StatefulSet для `kubectl apply`. Оператор и его CRD/RBAC остаются отдельным проверенным bootstrap, а созданные CNPG дочерние ресурсы не перехватываются Helm.

Отдельный релиз на каждый API, notification-worker, frontend и gateway. Отдельные инфраструктурные релизы: `platform-config` (Secrets/ConfigMaps/NetworkPolicy), `postgres` (CNPG Cluster), `redpanda`, `mailpit`, `prometheus`, `tempo`, `otel-collector`, `grafana`. Общий chart приложения не объединяет их историю или выпуск. Все операции явно фиксируют context `k3d-sso-remediation` и namespace `sso-remediation`; это local/dev доставка, не AWS deployment.

Существующий до Helm стенд переносится явно: `make helm-adopt`, затем `make up`. Adoption сначала проверяет весь inventory, selectors, владельцев и credentials; только после этого меняет Helm metadata с проверкой UID/resourceVersion. Ничего не удаляет/пересоздаёт, не использует `--take-ownership`. Прерванный metadata-перенос можно повторить. На пустом стенде adoption не нужен. PVC и PostgreSQL Cluster имеют retention `keep`; uninstall не является штатной командой очистки или восстановления.

```sh
make releases
make release SERVICE=profile-service \
  IMAGE='registry.example/team/profile@sha256:<64-hex-digest>' \
  PROBE='uv run --no-project python scripts/acceptance/run.py probe'
# Для локального образа допустим только проверенный sso-remediation/<name>:sha256-<image-ID>.
# TIMEOUT=240 — ожидание каждого Helm rollout; image import/migration/probe имеют отдельные пределы.
make acceptance GATE=rolling
make release-rollback SERVICE=profile-service REVISION=1 \
  PROBE='uv run --no-project python scripts/acceptance/run.py probe'
```

`release` проверяет исходный бизнес-сценарий, импортирует только выбранный immutable image, запускает только миграцию DB owner выбранного API и обновляет только его Helm-релиз. Worker использует схему notification и сам миграцию не запускает. Приложения ждут готовности: maxUnavailable0/maxSurge1, minReadySeconds5, progress deadline180s; preStop5s плюс grace50s дают процессу завершить запросы/работу. HPA управляет replicas API: Helm их не сбрасывает при обновлении. Наличие свободных ресурсов обязательно; soft topology spread не доказывает разнесение копий на любых двух физических EC2.

Неудачная readiness останавливает выпуск и возвращает предыдущую конфигурацию приложения; первая установка поверх adopted ресурсов не выполняет destructive auto-uninstall. После readiness выполняется переданный business probe; его отказ также возвращает предыдущую успешную ревизию, но команда завершается ошибкой. Успешный выбранный image атомарно сохраняется в `.local/release-images.json`: обычный последующий `make up` не возвращает старый image из full-build lock. Full build и независимый release — разные операции; full build не публикует образы в registry. Проверка probe должна соответствовать сервису: login/profile не доказывает доставку worker или корректность frontend.
Успех приложения требует также завершённого `kubectl rollout status`: одной Helm legacy readiness недостаточно, она может вернуть управление до удаления старых копий. `release-rollback` выполняет конфигурационный возврат под тем же lock, ждёт полный rollout, согласует selected image и проверяет business probe. Full `up` сверяет сохранённые selections с фактически deployed Helm values: ручной успешный Helm rollback не переигрывается обратно старой записью. Failed/pending состояние не переопределяется молча.

Миграции назад не выполняются. Выпуск обязан сохранять совместимость старых/новых HTTP/gRPC клиентов, Kafka producers/consumers и сохранённых событий: сначала добавить совместимое поле/схему, затем перевести потребителей/данные, удалить старое отдельным выпуском после закрытия окна возврата. Helm не проверяет семантику контрактов. Воркер обновляется через consumer rebalance/at-least-once и идемпотентность, а не HTTP-процент canary; external SMTP exactly-once не обещается. Canary/blue-green и автоматический анализ метрик сейчас не внедрены.
Rekey сериализован с up/release/rollback/alert maintenance. До остановки writers проверяется путь финальной публикации: существующий Helm owner либо строго проверенный original unmanaged Secret до первого Helm-переноса. Только этот одноразовый legacy путь допускает UID/resourceVersion/data-tested JSON patch без apply и перехвата владельца. Повтор после частичного rekey сверяет protected precommit/complete key archives; произвольный credential drift не принимается.

Helm values, manifests, release Secrets и `.local/helm-failures/*.json` могут содержать credentials. Не публиковать `helm get values/manifest`, `--debug`, dry-run output или сырые diagnostics. Ошибки показывают только путь к protected0600 diagnostics; история/статус CLI выводятся без notes/description. Helm history не шифрует values самостоятельно; права на Kubernetes Secrets — доступ к секретам.

Если первая install завершилась `failed`, успешной ревизии для rollback ещё нет: устраните причину по protected diagnostics и явно продолжите `helm upgrade RELEASE charts/CHART --kube-context k3d-sso-remediation -n sso-remediation -f PRIVATE_VALUES --server-side=false --wait=legacy --timeout 240s --history-max 20`, сохранив values0600 в каталоге0700. Не добавлять uninstall, cleanup-on-fail, force-replace, take-ownership, rollback-on-failure для первого восстановления; не удалять Helm Secrets. `pending-*` требует проверки незавершённого Helm процесса и отдельного recovery, конкурирующие writes запрещены. Для успешного приложения используйте `make release-rollback` с проверенным номером ревизии и реальным probe. Базы и Kafka автоматически назад не откатываются. Alert acceptance восстанавливает только свою временную platform-config конфигурацию bounded explicit upgrade, допускающий завершившийся failed, но не конкурирующий pending; общая политика infra auto-rollback не ослабляется.


## Реальная проверка и отказ

```sh
make test
make schema-gate
make persistence
make backup
make restore-verify BACKUP=.local/backups/<конкретный-каталог>
make alerts
make chaos TARGET=identity-service PROBE=/absolute/path/to/real-business-probe
# TARGET=postgres|redpanda|mailpit также поддерживаются
```

Fault commands сериализованы `flock`; второй concurrent injection отклоняется. SIGTERM переводится в cancellation exception с ожиданием безопасного writable primary и cleanup только собственной disposable DB, исходная ошибка не маскируется cleanup failure. `persistence-active-*.json` до удаления pod сохраняет имя DB и hash известного значения, результат содержит elapsed и before/after UID. CNPG graceful shutdown явно30секунд smart,60stop, вместо defaults180/1800; fast shutdown сохраняет checkpoint/WAL и не равен `--force`/SIGKILL. Primary replacement остаётся отдельным реальным fault, не подменяется удалением standby. При cancellation SIGKILL/выключении хоста cleanup не обещается: active marker нужен оператору для безопасного последующего восстановления.

`schema-gate` запускает настоящий identity image против отдельной пустой DB: требует live200/ready503, выполняет настоящую migration, затем требует ready200; disposable DB/Job/policies удаляются. `persistence` создаёт отдельную DB, записывает случайное значение, удаляет реальный primary pod, требует нового primary и сохранённого значения. `chaos` обязательно запускает переданный бизнес-probe до и после, проверяет существование target и удаление исходного UID. Он подтверждает **pod replacement**, не сетевую partition, отсутствие каждого пользовательского error во время failover или потерю хоста. Probe должен проверять именно затронутый бизнес-контракт: для SMTP доставки нужен delivery probe, одного login недостаточно. При невозможности injection/recovery команда завершается ошибкой. Parent acceptance harness выполняет полноценные UI/API/email/OIDC/negative проверки отдельно.

`make check` проверяет infra readiness и HTTPS discovery, **не заменяет бизнес-приёмку**. `alerts` временно добавляет rule, требует от настоящего Prometheus API `AcceptanceProbe state=firing`, сохраняет `.local/alert-verification.json` и восстанавливает production rules. Grafana provisioned dashboard показывает readiness, HTTP errors/latency, outbox age/pending, jobs/attempts и lag. Collector OTLP4318 экспортирует в Tempo; отсутствие телеметрии приложений не считается успешной trace-приёмкой. Требуются реальные spans HTTP→outbox→Kafka→delivery и соответствующий Tempo поиск при integrated acceptance.

## Хранение, HA и backup policy

CNPG:3 instances, synchronous commit1 standby, fencing/failover; Redpanda:3 brokers, replication3 и6 partitions, retention публичного topic7суток, encrypted notification commands1сутки. Durable boot задаёт `developer_mode:false` и явный `--unsafe-bypass-fsync=false`; `write_caching_default:disabled` запрещает обход через topic override. TLS/SCRAM/ACL и authenticated loopback Admin сохранены. Node properties находятся в broker config, cluster properties — в `.bootstrap.yaml` для первого запуска и `rpk cluster config set` с проверкой typed Admin JSON для retained cluster (`rpk config get` выдаёт YAML). 512MiB/1core — ограниченный local runtime, не vendor production sizing; `--overprovisioned` меняет scheduling, `--check=false` отключает только rpk host checks, не broker checks/fsync. PVC retained у StatefulSet, CNPG/PVC не удаляются lifecycle командами. `make stop/start` сохраняет Docker volumes. Local-path и Docker volumes требуют сохранности хоста. Обнаруженный старый dev boot реально обходил fsync даже при write cache false; исправление конфигурации не доказывает восстановление ранее подтверждённых Kafka записей. [Runbook и честные recovery gates](docs/acceptance.md#broker-durability-and-whole-host-recovery).

Локальная integrated acceptance 2026-10-23 (исполнена controller/Main): encrypted backup4DB20.66с, disposable restore с source row hashes24.59с; повторное systemd backup service исполнение20.98с, Result=success/ExecMainStatus0, timer active (сам timer trigger на момент записи не наблюдался). Изолированный primary persistence fault после исправления прошёл77.95с wall/75.879с по evidence: удалён primarypostgres2, появился новый UID, все3instancesReady, primarypostgres1, hash заранее записанного disposable значения совпал. Это pod/primary replacement и сохранность данных на одном хосте, не host/zone HA.

До исправления зафиксированы реальные failures: отменённый первый fault и повторная injection попали в незавершённый shutdown; CNPG defaults180сек smart/1800stop и попытка cleanup через Terminating primary скрыли исходную ошибку. Кластер восстановился естественно, без force kill; surviving disposable DB содержала1строку, старый неизвестный token не объявлялся совпавшим. Затем добавлены serialization/cancellation cleanup, Ready writable-primary gate и explicit30/60 shutdown. Первый запуск scheduled service совпал с primary maintenance и завершился ошибкой; после readiness/concurrency gate service реально прошёл. Ни один из этих failure не выдаётся за успешную приёмку.

Три container node одного компьютера **не являются независимыми failure domains**. PDB/spread/HPA защищают от части pod disruptions, не потери машины. API HPA CPU70% относительно requests,2–4 replicas; worker не autoscale CPU: требуется lag-aware control и верхняя граница6 partition consumers. Node autoscaling не реализован и не заявляется.

Backup — **логический snapshot, не PITR**, отдельно согласованный для каждой DB; распределённый atomic snapshot не обещается. pg_dump и source row hashes получают один exported transaction snapshot; encrypted dump+encrypted reference hashes защищены AES256-CBC/PBKDF2(600000)+encrypt-then-HMAC-SHA256 с постоянным backup key. Restore проверяет authentication до дешифрования, восстанавливает только уникальную disposable DB, сравнивает canonical row-content hashes со snapshot source и удаляет только свою DB. Реальные durations находятся в manifest/restore-verification. Все три owner `.env`, публичный CA и historical rekey manifests нужно защищённо сохранять отдельно: DB dump не восстанавливает ключи. `.local/backup.key` — derived копия canonical `platform-infra/.env` `BACKUP_ENCRYPTION_KEY`, не новый ключ; точные bytes/newline обязательны для старых backup. Не отправляйте ключ вместе с backup в публичное хранилище.

`make schedule-backups` явно устанавливает systemd **user** timer hourly, проверяет active; без работающего user manager завершается ошибкой. Для постоянного исполнения WSL/user manager должен быть активен; `systemctl --user list-timers sso-remediation-backup.timer` и `journalctl --user -u sso-remediation-backup.service` показывают реальные исполнения. Policy: hourly snapshots, retention7дней, каждый release перед cutover — manual backup+restore verify. Автоудаление backups не выполняется: архивы старше7дней удаляет оператор только после успешной restore verification и отдельного копирования key+archive в защищённое внешнее место. Пока этого нет, единственный host остаётся общей точкой потери данных; RPO≤1ч не заявляется без наблюдения timer executions. WAL archive/PITR/cloud object storage не настроены.

Ручные и scheduled backup используют общий fault lock с bounded ожиданием до300секунд; chaos/persistence/restore при коллизии fail-fast. Никакая коллизия не считается выполненным fault или успешным backup, deadline остаётся явной ошибкой. Перед snapshot ожидается ClusterReady и проверенный writable primary; transient maintenance не отправляет SQL в Terminating pod. Ошибка snapshot остаётся исходной даже при ошибке cleanup keeper. Active timer, успешный ручной service и реальный timer trigger проверяются отдельно.

## Безопасность и CI

Default deny ingress+egress, DNS исключение, явные app↔DB/broker/HTTP/OTLP пути, внешний443 только Telegram components. K3s network-policy controller включён; реальная приёмка доказывает deny untrusted pod и permitted paths. Application ServiceAccounts без RBAC/automount; nonroot, capsdropALL, no privilege escalation, seccomp, readonly root FS и bounded resources. CNPG использует аутентифицированный upstream manifest с проверяемым namespace-scoped overlay: operand Role только в sso-remediation, отдельные cache/PKI/leader права в cnpg-system, clusterRole только node/catalog reads и get/patch собственных webhook configurations по имени. WATCH_NAMESPACE не заменяет RBAC. Лишние bindings/неизвестные права и изменённые built-in discovery roles блокируют установку. Image/OPERATOR_IMAGE_NAME указывают на один проверенный artifact; локальные imported images используют IfNotPresent.

CNPG instance-manager требует Kubernetes API: `scripts/api_network.py` получает реальные ClusterIP и ready EndpointSlices Service `default/kubernetes` и разрешает **только** exact /32(/128) адреса:443 и DNAT endpoint:6443 для pod selector `cnpg.io/cluster=postgres`. Это не общий namespace egress443; приложение не получает API access. На новом кластере endpoint discovery повторяется перед DB readiness. При изменении control-plane адресов выполните повторный `up`, чтобы актуализировать policy.

Workflow `.github/workflows/verify.yml` проверяет pinned checkout/uv checksum, поведенческие тесты, конфигурацию мониторинга, секреты, IaC и Kubernetes schemas. Full-history secret gate с redaction выполняется до dependencies/build; временные credentials удаляются. Application workflows сохраняют настоящие сборки immutable images, lint/typecheck/integration/contract tests. Vulnerability scans образов и зависимостей по решению владельца отсутствуют во всей экосистеме и не являются release gate. Ничего не деплоится в облако автоматически. Наличие workflow не заменяет результат реального CI.

`PATCHED_COMPONENTS` явно перечисляет gateway/Grafana/Tempo/CNPG. `make build` сохраняет genuine package/source extensions и hash всех input files вместе с base/tag/imageID; `up` проверяет идентичность и импортирует их перед apply. Grafana содержит полный подписанный Prometheus/Tempo plugin bundle с pinnedSHA256 и выключенными startup downloads/updates; подписи не обходятся. Tempo сохраняет обновлённый tzdata; CNPG — исправленные обе manager architectures и CA. Проверка идентичности образов, provenance и соответствующих исходников остаётся независимо от удалённого vulnerability scanner.

Image `HEALTHCHECK` не заменяет Kubernetes probes. Gateway проверяет strict-TLS `/health/live` через штатную CA; Grafana helper проверяет HTTP200/JSON/database/version. Tempo helper проверяет HTTP200/ready. CNPG helper проверяет HTTPS127.0.0.1:9443/readyz с явным доверенным mounted public tls.crt и ServerName cnpg-webhook-service.cnpg-system.svc, без чтения private key и без TLS bypass. Все helper requests ограничены2s/4096bytes, не используют proxies/redirects, выводят фиксированный nonsecret status. Для штатной проверки нужны соответствующие конфиги/сертификаты. Health не означает отсутствие уязвимостей.

Текущая приёмка ограничена локальным Docker/k3d. По явному решению пользователя внешнее размещение и автоматическое восстановление всего хоста сейчас не являются критериями завершения; новых host fault injections нет. Исторические отчёты сохранены отдельно. AWS/EKS/RDS/MSK не создаются и не проверяются.

### Отдельный бенчмарк регистрации

```sh
make benchmark-registration
make benchmark-registration ARGS='--users 200 --workers 8'
```

Измеряет только настоящий `POST /api/v1/auth/register` через HTTPS gateway: Argon2, SQL-транзакция пользователя/роли/challenge/outbox. Уникальные `example.invalid` адреса, CSRF/Origin и проверка CA включены; подготовка клиентов/CSRF, подтверждение email, login и асинхронная доставка не входят в тайминг. Closed-loop генератор: `users` 1..200, `workers` 1..32 (по умолчанию 40/4), без повторов и подмены IP. Отдельно выводятся успешные регистрации/с, попытки/с, HTTP-коды, транспортные/некорректные ответы, p50/p95/p99/max успешных и всех запросов. Percentiles — nearest rank; быстрые `429` не уменьшают latency успешных регистраций.

Rate limits не изменяются: 20 попыток за 10 минут на IP-бакет; local proxy/SNAT может давать несколько gateway-observed адресов одному генератору. Поэтому лимит не равен 20 попыткам на весь локальный запуск. Результат с частичным throttling — `completed_with_throttling`, не доказательство предельной capacity. Полностью ограниченный запуск — `blocked`, exit 2 и null successful latency; прочие ошибки — exit 1. JSON каждого запуска сохраняется отдельно в `.local/acceptance/registration-benchmark-<run_id>.json` (0600), без паролей, токенов и тел ответов. Созданные неподтверждённые пользователи сохраняются с префиксом `benchmark-register-<run_id>`; пользовательские данные и rate-limit counters не очищаются. Бенчмарк сериализован с maintenance через общий lock и не входит в обычный core acceptance.

## Полный интерфейс оператора

Все Make targets объявлены `.PHONY`; Python entrypoints используют `uv run --no-project python` (override `PYTHON` только для выбранного локального interpreter). `uv run --no-project python scripts/cli.py --help` показывает CLI, `<command> --help` — только допустимые параметры этой команды. Отсутствующие/пустые `BACKUP`, `PROBE`, некорректные shell quotes в probe и чужие command options отвергаются до tool checks, lock и обращения к cluster. Probe исполняется как argv без shell: pipelines/redirections требуют явного `sh -c`. `BACKUP`, `PROBE`, `TARGET`, `GATE` передаются как одиночные аргументы; буквальный `$` в command-line Make variable записывается `$$`. `ARGS` для `rekey`/`acceptance` — намеренно список CLI arguments, а не один строковый аргумент.

| Make target | Реальная операция / обязательное условие |
| --- | --- |
| `bootstrap` | CLI `secrets`: создать/сохранить local secrets/certs; legacy key блокирует неявный cutover. |
| `build` | Pull pinned images, Docker builds, immutable lock; интернет и соседние source repos; длительная операция. |

Рекомендуемый порядок: contracts `generate`/`test`/две schema `compatibility`; infra `test` → `bootstrap` → `build` → `up` → `status` → `check` → `bootstrap-owner` → `schema-gate` → `backup` → `restore-verify` → `alerts`; затем port-forwards и acceptance core/дополнительные gates; затем по одному `persistence`/`chaos` с `check` и business probe после каждого. `stop` → `start` → дождаться `check` → возобновить port-forwards → business probe. Shared-host outage — отдельный согласованный этап после backup/restore, не вместе со сборками, scheduled backup или другими faults. `repair-certificates` и обе формы `rekey` проверяются только на соответствующих безопасных legacy fixtures, не через создание legacy key в рабочем stand. `schedule-backups` проверяется отдельно по active timer, реальному service execution и timer trigger; перед faults не допускайте concurrent backup.

Host controller ограничивает subprocess deadlines и выполняет реальные per-node `/readyz`, NodeReady и CNPG operator gates, а не только доступность общего API. `scripts/acceptance/host_state.py` использует конкретный32hex run-id и isolated base/CA/state для prepare/readiness/verify/cleanup: сохранённый реальный profile/session и committed DB marker проверяются после recovery. Cleanup собственной fixture и восстановление исходного backup timer обязательны до PASS.

### Неизменяемая сетевая identity и maintenance gate

Новый cluster создаётся с `k3d5.9.0 --subnet auto`: subnet выбирается из реально свободной Docker адресации, а managed IPAM назначает **static Docker IPAMConfig всем трём server peers**. Это подтверждено [CLI v5.9](https://k3d.io/v5.9.0/usage/commands/k3d_cluster_create/), [обработкой `auto`](https://github.com/k3d-io/k3d/blob/v5.9.0/pkg/config/transform.go), [server IP assignment](https://github.com/k3d-io/k3d/blob/v5.9.0/pkg/client/cluster.go) и [Docker endpoint translation](https://github.com/k3d-io/k3d/blob/v5.9.0/pkg/runtimes/docker/translate.go). Фиксированного глобального172.x subnet нет. Upstream не pins serverlb: его IP не является etcd identity, proxy разрешает фиксированные имена server nodes. Guard сохраняет существующий static serverlb reservation, если он есть, но не требует его для нового cluster.

`make cluster-identity` / `uv run --no-project python scripts/cli.py cluster-identity` не останавливает containers и не меняет Docker/Kubernetes: единственная запись — create-once local manifest0400 с checksum, без токенов, kubeconfig, сертификатов, паролей и полных inspect документов. Baseline выводится из **Ready Kubernetes Node InternalIP + исходных `etcd.k3s.cattle.io/node-address`/`node-name` + Node UID**, а не текущей Docker очередности; каждый IP обязан уже совпадать с explicit static IPAMConfig и живым endpoint. Проверяются ровно3peers, exact network ID/name/subnet/gateway и container IDs, уникальность IP/UID, отсутствие чужих endpoints/дополнительных сетей и пересечения subnet с PodCIDRs. Первичная запись при dynamic IP, несовпадении с persisted etcd annotation или неготовых узлах запрещена. Повторный запуск только проверяет неизменность; checksum/private permissions защищают от случайной порчи, **не от злонамеренной root-подмены**. Хранить manifest вместе с private local recovery state; не редактировать/удалять для обхода gate.

`up` существующего cluster требует baseline и live совпадения до применения workloads; новая установка записывает baseline после NodeReady. `start` сначала проверяет persisted baseline и Docker network/static endpoint configuration без Kubernetes API (работает для остановленных containers, **Docker daemon должен отвечать**), затем выполняет bounded existing-cluster start, NodeReady и live identity check. Непрошедшая post-start проверка не выдаёт ready и не пытается переподключить/сбросить узлы. Host-fault preflight сначала запускает read-only guard через Ubuntu WSL: broken Desktop integration, dynamic peer или drift отвергаются **до timer pause, backup, fixtures и injection**; final recovered gate также сверяет identity. Наличие guard не доказывает whole-host durability/HA и не объясняет причину WSL/kernel failure. Новый host fault/restart Docker/WSL shutdown ради проверки не разрешён.

**Только отдельно согласованное maintenance для старого dynamic cluster:** сначала сохранить исходное соответствие node-name→NodeUID→InternalIP→etcd annotation из здорового Kubernetes/pre-fault evidence и encrypted backup; если API недоступен или эти источники расходятся, остановиться и расследовать original peer identity, не брать новый Docker IP за baseline. Проверить фактические network ID/subnet, отсутствие чужих endpoints/IP conflicts и сохранить network aliases. Maintenance window с остановкой **только трёх owned server containers и owned serverlb** требует отдельного разрешения; не останавливать Docker Desktop/WSL и не трогать чужие containers. Только оператор в этом окне может disconnect/connect каждый exact owned container к **той же** сети с `docker network connect --ip <исходный-InternalIP> --alias <исходный-node-name> <network-ID> <container-ID>` (после его явного disconnect), сохранив прежние aliases. Никогда не использовать shuffled post-crash адреса, `cluster-reset`, удаление containers/PVC/volumes, автоматический pinning или rebaseline. Затем явно запустить те же containers, проверить все3 NodeReady/per-node API/etcd, исходные UID/annotations, CNPG/broker quorum и прежние business/session/profile/data proofs, и только затем `make cluster-identity`. На уже восстановленном static cluster достаточно последней read-only команды; maintenance не повторять.

Безопасная отдельная сверка **без создания baseline**: `uv run --no-project python scripts/cluster_identity.py verify`; для уже остановленных nodes — `... scripts/cluster_identity.py prestart`. Эти команды не стартуют cluster, не изменяют сетевые endpoints и не инжектируют fault.


Whole-host helper сохраняет реальные Kafka acknowledgements и SHA256 key/value по точным topic/partition/offset, затем проверяет те же записи без нового produce или изменения consumer groups. Во втором фактическом VM fault после ручного восстановления совпали все6RF3 partition markers и46выборочных исторических записей. Проверка также сохранила исходную сессию, профиль и DB marker. Это подтверждённая сохранность проверенных данных после manual recovery, не автоматическое восстановление и не доказательство каждой записи. Маленькие owned Kafka records имеют retention24h; metadata topic сохранена.

**Оба фактических whole-Docker-Desktop-host fault завершились FAIL. Новых host/WSL/Docker outage injections не выполнять.** Первый запуск потребовал ручного старта существующих nodes после cgroup admission error; второй привёл к потере Docker/Ubuntu WSL integration и перестановке динамических node IP, несовместимой с сохранёнными etcd peer identities. Штатный Desktop restart восстановил integration; возврат исходных адресов тем же containers как static IPAM и последовательное восстановление broker RPC сохранили PVCs, прежнюю session/profile/DB и проверенные Kafka records. После этого все3узла/API/etcd/CNPG/apps/broker quorum, HTTPS и core/admin acceptance прошли. Исходные FAIL reports сохранены; подробная последовательность и ограничения — `docs/acceptance.md`, актуальный статус публикации — `docs/handoff.md`. Identity guard предупреждает известный network drift без остановки сервисов, но не превращает два неуспешных автоматических восстановления в PASS.

## Copyable source workspace

Исходники шаблона — девять независимых Git repositories: `platform-infra`, `platform-contracts`, `identity-service`, `user-notification-service`, `frontend`, `catalog-service`, `billing-service`, `subscription-service`, `referral-service`. Для fresh-copy проверки используйте отдельные reviewed clean Git repositories (или временные Git fixtures), содержащие реальные commits. # Parent каталоги PINNED и DESTINATION должны существовать; сами пути — ещё нет.
```sh
set --
for owner in platform-infra platform-contracts identity-service user-notification-service frontend catalog-service billing-service subscription-service referral-service; do
  set -- "$@" --local "$owner=$SOURCE_ROOT/$owner"
done
uv run --no-project python scripts/workspace.py resolve \
  --manifest workspace.sources.json --output "$PINNED" "$@"
# Проверить реальные commit IDs в PINNED; resolve не создаёт workspace.
uv run --no-project python scripts/workspace.py checkout \
  --manifest "$PINNED" --destination "$DESTINATION" "$@"
```

`checkout` создаёт новый workspace с detached HEAD ровно на выбранном lowercase40 commit каждого owner и сохраняет выбранные sources в `DESTINATION/workspace.sources.json`. Движение исходного `HEAD` после resolve не меняет выбранный commit. Missing/duplicate owners, invalid SHA/URL, traversal, symlinks, dirty local inputs, tracked private/build paths и любой occupied destination (даже пустой) отклоняются; существующие данные не перезаписываются. Submodules и tracked symlinks требуют отдельного проектного решения и сейчас не поддержаны. Нет recursive source copy, автообновления main, выполнения arbitrary templates или source Git hooks. Git working-tree content берётся только из выбранных Git objects.

Для публичного pinned release после **отдельно разрешённой фактической публикации** внесите настоящие `https://github.com/OWNER/REPO` URL во все entries, удалите `local`, `local_path`, поставьте `revision: null`, при желании `ref: "main"`. Команда `resolve --manifest published-sources.json --output release-sources.pinned.json` явно читает только `refs/heads/main` каждого remote и сохраняет реальные commit IDs в новый файл. Затем `checkout --manifest release-sources.pinned.json --destination /absolute/new-workspace` получает exact detached revisions, а не floating main. HTTPS URL не допускает credentials/query/fragment/port. Нельзя придумывать remote SHA для неопубликованных repositories или публиковать local path metadata. Reviewed совместимость этих commits и отдельно immutable image digests — обязанность выпуска; checkout не подтверждает application readiness или external-provider acceptance.

Owner управляет публичной конфигурацией frontend через обычный `/config.json`, образец — `config.example.json`: `brand.name`, optional `brand.logo_url`/`brand.help_url`, `locales`, `default_locale`, `canonical_origin`. Поставьте собственный logo asset по указанному same-origin пути или удалите optional logo URL; help задаётся HTTPS URL. `canonical_origin` должен **точно** совпадать с реальным browser origin, например `https://localhost:18448` только для изолированного generic profile. Изменения конфигурации не меняют API transport origin и не исполняют JavaScript. Это только публичные значения, не provider credentials или purpose keys. Секреты создаются owner-specific bootstrap существующим delivery workflow, не source checkout. MIT распространяется на собственный код; third-party licenses/notices сохраняются. Перед публикацией нужен redacted full-history secret review; path exclusions не заменяют secret scan. Подробнее: `SECURITY.md` и `CONTRIBUTING.md`.

Поведенческие Git/filesystem regressions: `uv run --no-project python -m unittest discover -s scripts/tests -p 'test_workspace.py'`. Эта проверка не заменяет общий integration/build/runtime/browser acceptance; текущие delivery commands и требования перечислены выше.

## Изолированный generic profile

Этот режим предназначен только для локальной приёмки: фиксированный namespace `generic-subscriptions` в явно выбранном `k3d-sso-remediation`, HTTPS18448/HTTP18089 через loopback port-forward. Он не создаёт, не стартует, не останавливает cluster и не меняет исходный namespace, его operator/RBAC/webhooks, PVC или owner `.env`. Namespace создаётся эксклюзивно, затем private create-once `.generic-local/namespace-identity.json` связывает HTTPS loopback API, UID `kube-system` и UID собственного namespace. Уже существующий namespace без matching baseline не усыновляется; drift не исправляется автоматически.

```sh
uv run --no-project python scripts/cli.py --profile generic --context k3d-sso-remediation secrets
uv run --no-project python scripts/cli.py --profile generic --context k3d-sso-remediation build
uv run --no-project python scripts/cli.py --profile generic --context k3d-sso-remediation up
uv run --no-project python scripts/cli.py --profile generic --context k3d-sso-remediation bootstrap-owner
# Каждый forward — отдельный terminal/process.
uv run --no-project python scripts/cli.py --profile generic --context k3d-sso-remediation gateway
uv run --no-project python scripts/cli.py --profile generic --context k3d-sso-remediation gateway-http
uv run --no-project python scripts/cli.py --profile generic --context k3d-sso-remediation mailpit
# После HTTPS-forward:
uv run --no-project python scripts/cli.py --profile generic --context k3d-sso-remediation check
```

Все canonical credentials/private keys этого режима находятся только в ignored `.generic-local/owners/<repository>/.env`; TLS mounts, CA, backup key и immutable image lock — в `.generic-local`. Не копируйте туда исходные `.env`. Первый bootstrap может принять process `OWNER_EMAIL`/`OWNER_PASSWORD`; затем редактируется isolated identity owner env с этими именами. Существующий default store сохраняет исторические `ADMIN_EMAIL`/`ADMIN_PASSWORD` bytes как legacy storage mapping, но runtime Job/CLI называется только `bootstrap-owner` и передаёт `OWNER_*`.

Catalog8006, Billing8007, Subscription8008, Referral8009 имеют отдельные runtime/migration DB roles, DB, TLS private keys, service tokens, Kafka SCRAM identities и quarantine keys. Все8owner DB включены в существующие encrypted logical backup/restore commands; snapshots отдельные, не distributed atomic transaction. Generic PostgreSQL — **один локальный StatefulSet, не HA**, с собственным retained PVC и verify-full TLS. Это намеренный local-only вариант без изменения исходного namespace-scoped CNPG controller; исходный default profile сохраняет CNPG3. Проверен только image config: pinned PostgreSQL18.6 image имеет user26 и PostgreSQL18 binaries в PATH; запуск и реальная приёмка выполняются integration owner.

Generic Redpanda использует поддержанный pinned binary reactor `--reactor-backend=epoll` только в `generic-subscriptions` (`localEpoll:true`); default profile не меняется. Это локальный performance/resource tradeoff: epoll networking уменьшает расход общего Linux AIO pool при параллельной работе исходных и новых brokers, но не даёт обещания production throughput. Disk DMA/fsync не отключаются: `--unsafe-bypass-fsync=false`, RF3 и broker durability policy сохранены. Global sysctl, исходные brokers и host не изменяются. Выбор подтверждён integration owner фактическим `--help-seastar` pinned binary; реальная readiness/produce/consume проверка обязательна отдельно.

Prometheus собирает каждую Ready application replica отдельно через headless `<service>-metrics.<namespace>.svc.cluster.local` DNS A discovery, а не балансируемый Service VIP. Scrape pools имеют уникальные имена, общие labels `job=platform`, `app`, `service`, `owner`; `instance` — фактический podIP:port. HTTPS проверяет CA и canonical owner `server_name`, даже когда target — IP. Дополнительные API permissions/tokens не нужны. Полный application scrape config формируется из APPS в `release_values`; `observability/prometheus.yml` содержит только общий infrastructure base. Для counter/histogram acceptance нужны стабильные PodUID/restartCount и суммирование отдельных series, не смена replicas на1 или искусственные запросы.

Optional `NOWPAYMENTS_API_KEY`/`NOWPAYMENTS_IPN_SECRET` задаются только в `.generic-local/owners/billing-service/.env`. При отсутствии не генерируются fake values: provider readiness/operations обязаны честно отказать. Default URL — официальный HTTPS API; fixture overrides/fixture workload принадлежат отдельной явной acceptance процедуре и не входят в обычный deploy. Telegram и external integrations остаются отдельными real-credential gates. `EXTERNAL_EVENT_INTEGRATIONS` разрешён только profile owner env; HMAC ingress идёт через private gateway9443 только от workload `integration-ingress`, не публичный gateway443; произвольный `/internal/` снаружи закрыт.

Topic names берутся из contract registry: immutable legacy identity/notification v1 допускаются только для drain; новая envelope schema_version2 использует identity/profile/notification `.v2`, а новые business families catalog/billing/subscription/referral/external `.v1`. Grants exact topic/group без wildcard, encrypted commands читает только notification identity. Cluster IdempotentWrite нужен Kafka producer, но не даёт cross-owner topic WRITE. Provider HTTPS egress разрешён только profile/notification-worker/billing. Static render: `uv run --no-project python scripts/render.py --profile generic --output .generic-local/render.json`; output credential-bearing, не публиковать. Regression suite: `uv run --no-project python -m unittest discover -s scripts/tests -p 'test_*.py'`. Здесь не утверждается, что tests/build/render/runtime уже прошли.
