# Изолированная локальная платформа

Среда **local/dev**, кластер и namespace `sso-remediation`. HTTPS `https://localhost:8448`, HTTP `http://localhost:8089` перенаправляет на HTTPS. Старые кластеры, namespace и тома не изменяются. Docker Compose и прежние permissive manifests удалены из cutover; постоянный Dashboard cluster-admin и токен больше не provisionятся. Уже существующий чужой Dashboard автоматически не удаляется.

## Предварительные условия

Linux x86_64/WSL2, Docker Desktop/Engine, curl, OpenSSL, make, Python3.12+, uv0.13.5, k3d5.9.0, kubectl1.36.1 (minor34–36). Новый bootstrap фиксирует K3s1.35.9-k3s1; ранее проверенный существующий stand1.35.5 не обновляется/удаляется автоматически и явно отмечается maintenance gate. CNPG1.30.1 поддерживает Kubernetes1.34/1.35/1.36 и PostgreSQL14–18 по [официальной матрице](https://cloudnative-pg.io/docs/current/supported_releases/); PostgreSQL18.6-standard-trixie. `bash scripts/bootstrap-tools.sh` устанавливает проверенные binaries в `~/.local/bin` без sudo/globalCA. Совместимые tools переустанавливать не нужно. `export PATH="$HOME/.local/bin:$PATH"`. Docker рекомендуется≥16GiRAM; Tempo3.1.1 требует headroom до4Gi. Requests/limits в `scripts/manifests.py`.

Рядом должны находиться `identity-service`, `user-notification-service`, `frontend`, `platform-contracts`. Docker contexts ограничены owner whitelist; lockfiles обязательны. Инфраструктурные immutable digest pins: PG18.6, Redpanda26.2.5, Mailpit1.32.0, Prometheus3.15.1, Grafana13.2.4-distroless-slim, Tempo3.1.1, Collector0.163.2, nginx1.30-alpine. Реальный vulnerability gate **открыт** для upstream Kubernetes/PostgreSQL/Redpanda/Grafana; clean Mailpit/nginx candidates и полные результаты — [docs/security-images.md](docs/security-images.md), без CVE ignores. `build` сохраняет `.local/images.lock.json`: artifactDockerID tag отдельно от sourceSHA. Sourcehash игнорирует private.env/.gitfile и framing path/content обеспечивает переносимость между worktrees; смысловой sourcechange инвалидирует lock. `up` отклоняет source/image mismatch; изменение source во время build запрещает публикацию. Внешний package repository не объявляется bit-for-bit воспроизводимым; иной artifact получает иной tag. CNPG release проверяется officialassetSHA256.

Все secrets/certs/signing/backup keys находятся только в ignored `.local/` (directory0700, secrets0600), пароли не печатаются. Admin email/password — `.local/secrets.json`, ключи `admin_email`/`admin_password`; при первом bootstrap можно задать `ADMIN_EMAIL`/`ADMIN_PASSWORD`. Повтор bootstrap сохраняет credentials, не меняет пароль пользователя. Admin bootstrap требует MFA перед административными операциями. Ключи разделены: `MFA_ENCRYPTION_KEY` только identity; `DELIVERY_ENCRYPTION_KEY` только identity/notification/worker; `QUARANTINE_ENCRYPTION_KEY` отдельный для каждого Go owner. Старый общий ключ не используется. TELEGRAM_BOT_TOKEN optional, без него канал недоступен; реальный webhook `POST /internal/v1/telegram/webhook` защищён Telegram secret header. Для настоящей Telegram приёмки нужны bot token/chat и публичный HTTPS callback; localhost не подходит.

CA `.local/ca.crt` доверять явно через `curl --cacert` или отдельный browser profile. Каждому сервису выдаётся отдельный private key/cert в `.local/certificates/<service>/`; сертификат profile не удостоверяет identity. Только gateway имеет SAN localhost/127.0.0.1; broker SAN соответствуют short/full advertised DNS. Gateway проверяет upstream hostname и устанавливает X-Gateway-Token только identity (остальным upstream пустой), identity доверяет X-Real-IP только с этим secret. Общая CA не означает общий private key. PostgreSQL DSNs требуют `sslmode=verify-full` и CNPG-generated CA `/run/postgres/ca.crt`; host `postgres-rw.sso-remediation.svc`. Kafka29092 и interbroker RPC шифрованы TLS, SASL SCRAM-SHA256, ACL exact topic/group: profile/audit читают только public events; notification также encrypted commands; identity только производит. Bootstrap broker user доступен только broker/admin orchestration; admin listener9645 loopback и require-auth,9644 доступен только Prometheus по policy. Gateway блокирует произвольные /internal и /metrics, исключение — защищённый Telegram webhook.

Создание SASL users выполняется через loopback port-forward к3явно известным broker pods: orchestration читает controller leader_id, проверяет node_config выбранного pod и отправляет mutation только его localhost endpoint. HTTP redirects отключены; Authorization никогда не пересылается на адрес из Location. Смена лидера в момент mutation приводит к fail-closed ошибке, не открывает Admin API наружу.

Если существующий local CA создан без RFC-required keyUsage, strict Python/OpenSSL корректно отклоняет цепочку. Явная команда `make repair-certificates` переиздаёт CA и server certs с правильными critical extensions, сохраняя private keys, subject, serial и SAN; старые certificates архивируются, новые строго проверяются до атомарной публикации. Далее повторно примените TLS Secrets и перезапустите соответствующие deployments/stateful broker по очереди; CA не устанавливается глобально. Клиентские strict проверки не отключаются.

Bootstrap: новый cluster → CNPG controller → durable infrastructure → готовый DB/broker → отдельные migration/runtime роли и DB → конечные migration Jobs → топики → приложения. Миграции запускаются отдельными credentials; runtime получает DML/sequence privileges без CREATE. Ошибка mandatory шага останавливает команду. Jobs сохраняются сутки для диагностики, не игнорируются. Readiness приложений проверяет схему, liveness — процесс. Broker outage не должен ломать identity login, если SQL outbox может сохранять операции.

Migration/rekey Job использует bounded initContainer из pinned PostgreSQL image: тот же pod IP/labels и verify-full DSN выполняют `SELECT1` до60секунд, чтобы дождаться реализации NetworkPolicy для нового pod. Только TCP refused/timeout/DNS transient ошибки допускают повтор; authentication/TLS/SQL ошибки останавливают Job сразу. Собственно migration не повторяется и её ошибка не скрывается. Это необходимо потому, что kube-router применяет IP sets асинхронно после admission; положительные TCP controls проверены на всех3нодах, untrusted control запрещён и к ServiceIP, и напрямую к primary.

Legacy shared-key cutover не автоматический: наличие `encryption_key` в `.local/secrets.json` блокирует bootstrap/up. Только для **никогда не использованных** credentials `make rekey ARGS=--unused` проверяет отсутствие namespace и retained PV и архивирует старый ключ0600. Для populated среды `make rekey` требует drain outbox/jobs, committed=end всех6 sensitive topic partitions и истечения **уже настроенного** Kafka retention (start=end; topic не truncates/deletes). Нельзя произвольно reset offsets/replay historical ciphertext старым ключом после cutover. Затем останавливает все runtime writers, повторно проверяет drain, делает encrypted backup, выполняет idempotent advisorylocked transactional rekey CLI каждого DB owner. Старый ключ остаётся до успеха всех owners и затем сохраняется отдельным protected archive для старых backup. При ошибке runtime остаётся остановлен и legacy key сохраняется; повтор команды безопасен по owner markers. После успеха `make up` применяет новые purpose keys и возобновляет runtime. Это maintenance cutover с сохранением данных, не прозрачный runtime fallback.

Secrets manifests публикуются атомарно: same-directory0600 tempfile → flush/fsync → os.replace → directory fsync. Перед первым owner rekey Job сохраняется отдельный protected **полный** `rekey-precommit-*.json` (legacy плюс все target keys); после commit финальный archive также содержит весь key manifest. Поэтому crash после DB commit не теряет target keys. Не удаляйте precommit/final manifests до отдельной проверенной защищённой копии; они столь же чувствительны, как основной secrets.json.

## Реальная проверка и отказ

```sh
make test
make schema-gate
make persistence
make backup
make restore-verify BACKUP=.local/backups/<конкретный-каталог>
make alerts
make chaos TARGET=identity-service PROBE=/absolute/path/to/real-business-probe
# TARGET=postgres|redpanda|mailpit также поддерживаются
```

Fault commands сериализованы `flock`; второй concurrent injection отклоняется. SIGTERM переводится в cancellation exception с ожиданием безопасного writable primary и cleanup только собственной disposable DB, исходная ошибка не маскируется cleanup failure. `persistence-active-*.json` до удаления pod сохраняет имя DB и hash известного значения, результат содержит elapsed и before/after UID. CNPG graceful shutdown явно30секунд smart,60stop, вместо defaults180/1800; fast shutdown сохраняет checkpoint/WAL и не равен `--force`/SIGKILL. Primary replacement остаётся отдельным реальным fault, не подменяется удалением standby. При cancellation SIGKILL/выключении хоста cleanup не обещается: active marker нужен оператору для безопасного последующего восстановления.

`schema-gate` запускает настоящий identity image против отдельной пустой DB: требует live200/ready503, выполняет настоящую migration, затем требует ready200; disposable DB/Job/policies удаляются. `persistence` создаёт отдельную DB, записывает случайное значение, удаляет реальный primary pod, требует нового primary и сохранённого значения. `chaos` обязательно запускает переданный бизнес-probe до и после, проверяет существование target и удаление исходного UID. Он подтверждает **pod replacement**, не сетевую partition, отсутствие каждого пользовательского error во время failover или потерю хоста. Probe должен проверять именно затронутый бизнес-контракт: для SMTP доставки нужен delivery probe, одного login недостаточно. При невозможности injection/recovery команда завершается ошибкой. Parent acceptance harness выполняет полноценные UI/API/email/OIDC/negative проверки отдельно.

`make check` проверяет infra readiness и HTTPS discovery, **не заменяет бизнес-приёмку**. `alerts` временно добавляет rule, требует от настоящего Prometheus API `AcceptanceProbe state=firing`, сохраняет `.local/alert-verification.json` и восстанавливает production rules. Grafana provisioned dashboard показывает readiness, HTTP errors/latency, outbox age/pending, jobs/attempts и lag. Collector OTLP4318 экспортирует в Tempo; отсутствие телеметрии приложений не считается успешной trace-приёмкой. Требуются реальные spans HTTP→outbox→Kafka→delivery и соответствующий Tempo поиск при integrated acceptance.

## Хранение, HA и backup policy

CNPG:3 instances, synchronous commit1 standby, fencing/failover; Redpanda:3 brokers, replication3 и6 partitions, retention публичного topic7суток, encrypted notification commands1сутки. Durable boot задаёт `developer_mode:false` и явный `--unsafe-bypass-fsync=false`; `write_caching_default:disabled` запрещает обход через topic override. TLS/SCRAM/ACL и authenticated loopback Admin сохранены. Node properties находятся в broker config, cluster properties — в `.bootstrap.yaml` для первого запуска и `rpk cluster config set` с проверкой typed Admin JSON для retained cluster (`rpk config get` выдаёт YAML). 512MiB/1core — ограниченный local runtime, не vendor production sizing; `--overprovisioned` меняет scheduling, `--check=false` отключает только rpk host checks, не broker checks/fsync. PVC retained у StatefulSet, CNPG/PVC не удаляются lifecycle командами. `make stop/start` сохраняет Docker volumes. Local-path и Docker volumes требуют сохранности хоста. Обнаруженный старый dev boot реально обходил fsync даже при write cache false; исправление конфигурации не доказывает восстановление ранее подтверждённых Kafka записей. [Runbook и честные recovery gates](docs/acceptance.md#broker-durability-and-whole-host-recovery).

Локальная integrated acceptance 2026-10-23 (исполнена controller/Main): encrypted backup4DB20.66с, disposable restore с source row hashes24.59с; повторное systemd backup service исполнение20.98с, Result=success/ExecMainStatus0, timer active (сам timer trigger на момент записи не наблюдался). Изолированный primary persistence fault после исправления прошёл77.95с wall/75.879с по evidence: удалён primarypostgres2, появился новый UID, все3instancesReady, primarypostgres1, hash заранее записанного disposable значения совпал. Это pod/primary replacement и сохранность данных на одном хосте, не host/zone HA.

До исправления зафиксированы реальные failures: отменённый первый fault и повторная injection попали в незавершённый shutdown; CNPG defaults180сек smart/1800stop и попытка cleanup через Terminating primary скрыли исходную ошибку. Кластер восстановился естественно, без force kill; surviving disposable DB содержала1строку, старый неизвестный token не объявлялся совпавшим. Затем добавлены serialization/cancellation cleanup, Ready writable-primary gate и explicit30/60 shutdown. Первый запуск scheduled service совпал с primary maintenance и завершился ошибкой; после readiness/concurrency gate service реально прошёл. Ни один из этих failure не выдаётся за успешную приёмку.

Три container node одного компьютера **не являются независимыми failure domains**. PDB/spread/HPA защищают от части pod disruptions, не потери машины. API HPA CPU70% относительно requests,2–4 replicas; worker не autoscale CPU: требуется lag-aware control и верхняя граница6 partition consumers. Node autoscaling не реализован и не заявляется.

Backup — **логический snapshot, не PITR**, отдельно согласованный для каждой DB; распределённый atomic snapshot не обещается. pg_dump и source row hashes получают один exported transaction snapshot; encrypted dump+encrypted reference hashes защищены AES256-CBC/PBKDF2(600000)+encrypt-then-HMAC-SHA256 с постоянным local backup key. Restore проверяет authentication до дешифрования, восстанавливает только в уникальную disposable DB, сравнивает canonical row-content hashes со snapshot source, удаляет только свою DB; существующие DB не перезаписываются. Измеренные durations в manifest/restore-verification, не выдуманные RTO/RPO. Signing/encryption keys, CA и `.local/secrets.json` нужно сохранять отдельно вместе с `backup.key`: DB dump сам по себе не восстанавливает ключи. Не отправляйте ключ вместе с backup в публичное хранилище.

`make schedule-backups` явно устанавливает systemd **user** timer hourly, проверяет active; без работающего user manager завершается ошибкой. Для постоянного исполнения WSL/user manager должен быть активен; `systemctl --user list-timers sso-remediation-backup.timer` и `journalctl --user -u sso-remediation-backup.service` показывают реальные исполнения. Policy: hourly snapshots, retention7дней, каждый release перед cutover — manual backup+restore verify. Автоудаление backups не выполняется: архивы старше7дней удаляет оператор только после успешной restore verification и отдельного копирования key+archive в защищённое внешнее место. Пока этого нет, единственный host остаётся общей точкой потери данных; RPO≤1ч не заявляется без наблюдения timer executions. WAL archive/PITR/cloud object storage не настроены.

Ручные и scheduled backup используют общий fault lock с bounded ожиданием до300секунд; chaos/persistence/restore при коллизии fail-fast. Никакая коллизия не считается выполненным fault или успешным backup, deadline остаётся явной ошибкой. Перед snapshot ожидается ClusterReady и проверенный writable primary; transient maintenance не отправляет SQL в Terminating pod. Ошибка snapshot остаётся исходной даже при ошибке cleanup keeper. Active timer, успешный ручной service и реальный timer trigger проверяются отдельно.

## Безопасность и CI

Default deny ingress+egress, DNS исключение, явные app↔DB/broker/HTTP/OTLP пути, внешний443 только Telegram components. K3s embedded network-policy controller не отключён; integrated acceptance обязана доказать deny untrusted pod и положительные permitted paths. ServiceAccounts приложения не имеют RBAC и automount false. Nonroot, capsdropALL, no privilege escalation, seccompRuntimeDefault, readonly root FS, tmp emptyDir, requests/limits и PDB; CNPG controller использует только официальный controller RBAC/webhooks и свой database management account.

CNPG instance-manager требует Kubernetes API: `scripts/api_network.py` получает реальные ClusterIP и ready EndpointSlices Service `default/kubernetes` и разрешает **только** exact /32(/128) адреса:443 и DNAT endpoint:6443 для pod selector `cnpg.io/cluster=postgres`. Это не общий namespace egress443; приложение не получает API access. На новом кластере endpoint discovery повторяется перед DB readiness. При изменении control-plane адресов выполните повторный `up`, чтобы актуализировать policy.

Workflow `.github/workflows/verify.yml`: pinned checkout SHA/uv checksum, behavior tests, monitoring validation, IaC/secret/dependency image scans, generated Kubernetes schema validation. Full-history secret gate выполняется с redaction до dependencies/build; generated resource files остаются private и удаляются после сканирования. App repository workflows отдельно собирают/проверяют immutable application images. Любые оставшиеся runtime vulnerabilities **любой severity**, включая UNKNOWN/LOW/MEDIUM, останавливают image scan; severity/ignore исключений нет. Ничего не публикуется автоматически, cloud/deploy/push отсутствуют. Первая публикация workflow требует авторизованного push/PR: `workflow_dispatch` доступен только после попадания workflow в default branch. Наличие workflow — не доказательство реального remote run или его прохождения.

Gateway pin в `PINS` фиксирует только исходный registry **base**, а не запускаемый artifact. `make build` собирает `components/nginx/Dockerfile` с точными signed Alpine security revisions (`musl`/`musl-utils`1.2.6-r3, `zlib`1.3.2-r1), сохраняет content-addressed local tag, реальный image ID, base и SHA256 recipe в `images.lock.json`. Смена recipe/base требует rebuild; `up` сверяет ID до импорта в k3d. Права root используются только при сборке, runtime uid/gid101. `scan_images.py` сканирует Docker archive фактического проверенного gateway ID со всеми severity и непустым package inventory, записывает build provenance; без lock (включая свежий CI runner) сначала собирает gateway. Уязвимый исходный base не выдаётся за исправленный runtime и сохраняется в provenance; registry credentials/GHCR publication для local artifact не требуются.
Docker classic image ID может быть config digest, а containerd-backed Docker Desktop возвращает OCI index digest. `scripts/image_archive.py` не приравнивает их строковым исключением: проверяет SHA256 blobs и путь index→manifest→config в сохранённом archive, затем Trivy ImageID обязан совпасть с вычисленным config digest. Raw JSON и provenance сохраняются до inventory/identity validation, включая ошибочные результаты.

Image `HEALTHCHECK` не заменяет Kubernetes probes. Gateway выполняет `curl --fail --cacert /run/tls/ca.crt https://localhost:8443/health/live` с deadline2s и проверкой hostname/цепочки TLS, без proxy и `--insecure`; нужны штатные mounts конфигурации и TLS, bare upstream без них закономерно unhealthy. В optional custom Grafana recipe статический Go1.26.10 helper `/usr/local/bin/grafana-healthcheck` под UID472 без shell/proxy/redirect проверяет `http://127.0.0.1:3000/api/health`: HTTP200, корректный JSON, `database:"ok"` и непустой `version`, ≤4096bytes и deadline2s; выводит только фиксированный nonsecret status. Оба image checks запускаются каждые30s, timeout3s, retries3; start-period gateway10s/Grafana30s. Custom Grafana не выбран автоматически и этот check не закрывает оставшийся vulnerability gate.

AWS/EKS/RDS/MSK не создаются и не проверяются. Настоящее host/zone HA потребует независимых нод/storage/failure domains, controller RBAC review, внешнего TLS/secret/backup management и отдельных chaos/restore испытаний выбранной среды.

`make acceptance` запускает durable real API/negative/OIDC race/events/security gates из `scripts/acceptance`; `make acceptance GATE=admin|load|trace|failure|replay|smtp-fault` запускает дополнительные реальные сценарии. CA автоматически `.local/ca.crt`, state только ignored `.local/acceptance`, Mailpit loopback28026. ## Полный интерфейс оператора

Все Make targets объявлены `.PHONY`; Python entrypoints используют `uv run --no-project python` (override `PYTHON` только для выбранного локального interpreter). `uv run --no-project python scripts/cli.py --help` показывает CLI, `<command> --help` — только допустимые параметры этой команды. Отсутствующие/пустые `BACKUP`, `PROBE`, некорректные shell quotes в probe и чужие command options отвергаются до tool checks, lock и обращения к cluster. Probe исполняется как argv без shell: pipelines/redirections требуют явного `sh -c`. `BACKUP`, `PROBE`, `TARGET`, `GATE` передаются как одиночные аргументы; буквальный `$` в command-line Make variable записывается `$$`. `ARGS` для `rekey`/`acceptance` — намеренно список CLI arguments, а не один строковый аргумент.

| Make target | Реальная операция / обязательное условие |
| --- | --- |
| `bootstrap` | CLI `secrets`: создать/сохранить local secrets/certs; legacy key блокирует неявный cutover. |
| `build` | Pull pinned images, Docker builds, immutable lock; интернет и соседние source repos; длительная операция. |
| `up` | Создать только isolated cluster при отсутствии, применить operator/storage/network/migrations/apps; нужен актуальный `build` lock. |
| `check`, `status` | Readiness + strict discovery / listing pods,PVC,services,HPA,PDB. |
| `stop`, `start` | Остановить/запустить только isolated k3d cluster; durable volumes сохранены; после `start` отдельно `check`. |
| `cluster-identity` | Read-only Docker/K8s проверка исходных трёх peers; один раз создать private `.local/cluster-identity.json`, далее только сверять, никогда не перезаписывать. |
| `bootstrap-admin` | Реальный identity Job; действующая DB/schema/images; credentials остаются локально, далее MFA. |
| `schedule-backups` | Установить/enable hourly systemd user timer; работающий user manager; это persistent host configuration. |
| `backup` | Encrypted logical snapshots всех owner DB под fault lock; готовый writable primary и backup key. |
| `restore-verify BACKUP=...` | Обязателен один complete backup directory; disposable DB restore/hash comparison; исходные DB не перезаписываются. |
| `schema-gate` | Disposable identity DB/process: live200/ready503 → migration → ready200; свободен loopback18001. |
| `repair-certificates` | Explicit local certificate replacement/archive; не применяет Secrets и не рестартует runtime автоматически. |
| `rekey [ARGS=--unused]` | Только существующие legacy credentials; populated maintenance / доказанно unused bootstrap; не запускать на обычной новой purpose-key среде. |
| `chaos TARGET=... PROBE=...` | Ready pod deletion/replacement + обязательный business probe до/после; targets `identity-service` (default), `postgres`, `redpanda`, `mailpit`; destructive fault, строго последовательно. |
| `persistence` | Disposable DB marker + реальное удаление PostgreSQL primary; destructive fault, строго последовательно. |
| `alerts` | Временная rule + restart Prometheus + actual firing API + восстановление rules; требует свободного loopback29090, остановите внешний `make prometheus`. |
| `mailpit`, `prometheus`, `grafana`, `tempo` | Foreground loopback port-forward28026/29090/23000/23200; отдельные терминалы, Ctrl-C, возобновить после cluster/host outage. |
| `test` | Все Python behavior regressions, включая Make dispatch/argument boundaries; нужен make и OpenSSL. |
| `acceptance GATE=... ARGS=...` | Реальные API/security/fault/load gates; default `core`, prerequisite/sequence в [docs/acceptance.md](docs/acceptance.md). |
| `host-fault ALLOW_SHARED_HOST_OUTAGE=1` | **Весь Docker Desktop host**, включая чужие containers (`dsh-hindsight`): Windows external Python observer/backend crash/recovery через thin PowerShell wrapper; только после явного разрешения владельца, без concurrent jobs/faults. Без flag script должен отказать до mutation. Нужны WSL interop, `wslpath`, `powershell.exe`, Windows Python3 launcher `py.exe -3`, Docker Desktop. Это не независимая host HA. |

Рекомендуемый порядок: contracts `generate`/`test`/две schema `compatibility`; infra `test` → `bootstrap` → `build` → `up` → `status` → `check` → `bootstrap-admin` → `schema-gate` → `backup` → `restore-verify` → `alerts`; затем port-forwards и acceptance core/дополнительные gates; затем по одному `persistence`/`chaos` с `check` и business probe после каждого. `stop` → `start` → дождаться `check` → возобновить port-forwards → business probe. Shared-host outage — отдельный согласованный этап после backup/restore, не вместе со сборками, scheduled backup или другими faults. `repair-certificates` и обе формы `rekey` проверяются только на соответствующих безопасных legacy fixtures, не через создание legacy key в рабочем stand. `schedule-backups` проверяется отдельно по active timer, реальному service execution и timer trigger; перед faults не допускайте concurrent backup.

Host controller ограничивает subprocess deadlines и выполняет реальные per-node `/readyz`, NodeReady и CNPG operator gates, а не только доступность общего API. `scripts/acceptance/host_state.py` использует конкретный32hex run-id и isolated base/CA/state для prepare/readiness/verify/cleanup: сохранённый реальный profile/session и committed DB marker проверяются после recovery. Cleanup собственной fixture и восстановление исходного backup timer обязательны до PASS.

### Неизменяемая сетевая identity и maintenance gate

Новый cluster создаётся с `k3d5.9.0 --subnet auto`: subnet выбирается из реально свободной Docker адресации, а managed IPAM назначает **static Docker IPAMConfig всем трём server peers**. Это подтверждено [CLI v5.9](https://k3d.io/v5.9.0/usage/commands/k3d_cluster_create/), [обработкой `auto`](https://github.com/k3d-io/k3d/blob/v5.9.0/pkg/config/transform.go), [server IP assignment](https://github.com/k3d-io/k3d/blob/v5.9.0/pkg/client/cluster.go) и [Docker endpoint translation](https://github.com/k3d-io/k3d/blob/v5.9.0/pkg/runtimes/docker/translate.go). Фиксированного глобального172.x subnet нет. Upstream не pins serverlb: его IP не является etcd identity, proxy разрешает фиксированные имена server nodes. Guard сохраняет существующий static serverlb reservation, если он есть, но не требует его для нового cluster.

`make cluster-identity` / `uv run --no-project python scripts/cli.py cluster-identity` не останавливает containers и не меняет Docker/Kubernetes: единственная запись — create-once local manifest0400 с checksum, без токенов, kubeconfig, сертификатов, паролей и полных inspect документов. Baseline выводится из **Ready Kubernetes Node InternalIP + исходных `etcd.k3s.cattle.io/node-address`/`node-name` + Node UID**, а не текущей Docker очередности; каждый IP обязан уже совпадать с explicit static IPAMConfig и живым endpoint. Проверяются ровно3peers, exact network ID/name/subnet/gateway и container IDs, уникальность IP/UID, отсутствие чужих endpoints/дополнительных сетей и пересечения subnet с PodCIDRs. Первичная запись при dynamic IP, несовпадении с persisted etcd annotation или неготовых узлах запрещена. Повторный запуск только проверяет неизменность; checksum/private permissions защищают от случайной порчи, **не от злонамеренной root-подмены**. Хранить manifest вместе с private local recovery state; не редактировать/удалять для обхода gate.

`up` существующего cluster требует baseline и live совпадения до применения workloads; новая установка записывает baseline после NodeReady. `start` сначала проверяет persisted baseline и Docker network/static endpoint configuration без Kubernetes API (работает для остановленных containers, **Docker daemon должен отвечать**), затем выполняет bounded existing-cluster start, NodeReady и live identity check. Непрошедшая post-start проверка не выдаёт ready и не пытается переподключить/сбросить узлы. Host-fault preflight сначала запускает read-only guard через Ubuntu WSL: broken Desktop integration, dynamic peer или drift отвергаются **до timer pause, backup, fixtures и injection**; final recovered gate также сверяет identity. Наличие guard не доказывает whole-host durability/HA и не объясняет причину WSL/kernel failure. Новый host fault/restart Docker/WSL shutdown ради проверки не разрешён.

**Только отдельно согласованное maintenance для старого dynamic cluster:** сначала сохранить исходное соответствие node-name→NodeUID→InternalIP→etcd annotation из здорового Kubernetes/pre-fault evidence и encrypted backup; если API недоступен или эти источники расходятся, остановиться и расследовать original peer identity, не брать новый Docker IP за baseline. Проверить фактические network ID/subnet, отсутствие чужих endpoints/IP conflicts и сохранить network aliases. Maintenance window с остановкой **только трёх owned server containers и owned serverlb** требует отдельного разрешения; не останавливать Docker Desktop/WSL и не трогать чужие containers. Только оператор в этом окне может disconnect/connect каждый exact owned container к **той же** сети с `docker network connect --ip <исходный-InternalIP> --alias <исходный-node-name> <network-ID> <container-ID>` (после его явного disconnect), сохранив прежние aliases. Никогда не использовать shuffled post-crash адреса, `cluster-reset`, удаление containers/PVC/volumes, автоматический pinning или rebaseline. Затем явно запустить те же containers, проверить все3 NodeReady/per-node API/etcd, исходные UID/annotations, CNPG/broker quorum и прежние business/session/profile/data proofs, и только затем `make cluster-identity`. На уже восстановленном static cluster достаточно последней read-only команды; maintenance не повторять.

Безопасная отдельная сверка **без создания baseline**: `uv run --no-project python scripts/cluster_identity.py verify`; для уже остановленных nodes — `... scripts/cluster_identity.py prestart`. Эти команды не стартуют cluster, не изменяют сетевые endpoints и не инжектируют fault.


Whole-host helper сохраняет реальные Kafka acknowledgements и SHA256 key/value по точным topic/partition/offset, затем проверяет те же записи без нового produce или изменения consumer groups. Во втором фактическом VM fault после ручного восстановления совпали все6RF3 partition markers и46выборочных исторических записей. Проверка также сохранила исходную сессию, профиль и DB marker. Это подтверждённая сохранность проверенных данных после manual recovery, не автоматическое восстановление и не доказательство каждой записи. Маленькие owned Kafka records имеют retention24h; metadata topic сохранена.

**Оба фактических whole-Docker-Desktop-host fault завершились FAIL. Новых host/WSL/Docker outage injections не выполнять.** Первый запуск потребовал ручного старта существующих nodes после cgroup admission error; второй привёл к потере Docker/Ubuntu WSL integration и перестановке динамических node IP, несовместимой с сохранёнными etcd peer identities. Штатный Desktop restart восстановил integration; возврат исходных адресов тем же containers как static IPAM и последовательное восстановление broker RPC сохранили PVCs, прежнюю session/profile/DB и проверенные Kafka records. После этого все3узла/API/etcd/CNPG/apps/broker quorum, HTTPS и core/admin acceptance прошли. Исходные FAIL reports сохранены; подробная последовательность и ограничения — `docs/acceptance.md`, актуальный статус публикации — `docs/handoff.md`. Identity guard предупреждает известный network drift без остановки сервисов, но не превращает два неуспешных автоматических восстановления в PASS.
